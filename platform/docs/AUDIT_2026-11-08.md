# HotelBridge portal: technical audit, 8 Nov 2026

Scope: the new B2B portal only (`platform/`, https://portal.hotelbridge.co). The older CRM at app.hotelbridge.co (`frontend/`) was not audited or changed.

## A. Executive summary

The portal is sound underneath: real server-side authentication, a real Postgres database, agency isolation with tests, idempotent bookings and a truthful email log. Its biggest problem was speed, caused by code running on the other side of the world from the database.

- Fixed and live: the region (Singapore), branded emails, notification gaps, password reset.
- Built and tested, **waiting for approval to go live**: security patches, loading and error screens, static public pages, query reductions, indexes.
- **Needs an owner decision**: the default markups (section J).

## C. The `bom1::iad1` diagnosis

- `bom1` is the Vercel edge location that received the request (Mumbai). `iad1` is where the function ran (Washington DC). Verified: `vercel inspect` listed every function as `[iad1]`.
- Database in Singapore: verified from its hostname.
- So the theory was correct for dynamic pages: Mumbai → Washington → Singapore, with each database query crossing that long link.
- After the fix: `bom1::sin1`, and database queries take **3 ms** (measured from inside the function).
- Not measured: query time from Washington (the health check did not exist then). About 200+ ms per query is an estimate, not a measurement.
- Trap: deploying with the CLI from the repo root ignores `platform/vercel.json`. Always pass `--regions sin1`. Git-triggered builds should read that file, but this has not been verified yet.

## D. Performance

| Measure (from India) | Before | Singapore move (live) | With hardening (preview) |
|---|---|---|---|
| Homepage TTFB | 0.92–1.13 s | 0.37–0.76 s | **0.06 s** (CDN hit) |
| /login TTFB | 0.27–0.67 s | 0.59–0.66 s | 0.58 s, still dynamic |
| /register TTFB | 0.42 s | 0.53 s | 0.42 s; marked static in the build, but no cache-hit timing captured |
| Database query | not measured | not measured | 3 ms (96 ms on first connection) |

Cause of the slow dashboard: each admin click ran about 15 sequential queries, including 3 cleanup jobs that write to the database. Clean-ups now run at most once a minute, agent badge counts run in parallel, and admin issues are cached for 20 seconds.

**Not measured:** signed-in dashboard timings (I cannot sign in as you), Core Web Vitals (LCP, INP, CLS), and tests from Europe or North America. Neon's free plan sleeps when idle, so the first visit after a quiet spell will be slower; that delay has not been measured.

| Finding | Severity | Status |
|---|---|---|

| No rate limit or CAPTCHA on registration | Medium | Open |
| No Content-Security-Policy on app pages | Medium | Open |
| Email verification not required at registration | Medium | Open; manual agency approval mitigates it |
| `Access-Control-Allow-Origin: *` seen on a 404 from `/api/health` | Low | Seen only there; other routes not checked. Does not grant access to signed-in data |

Verified sound: protected routes redirect signed-out visitors (live); fake document and token links return 404 (live); the cron endpoint returns 401 without its secret (live); no secrets in browser bundles (scan of a local production build, which had no production secrets to leak, plus a search for secret names and key formats); HTTP-only cookies; hashed session and reset tokens; agency isolation test passes; `npm audit` shows 0 production vulnerabilities on the branch.

## F. Database

- Schema uses foreign keys and tracked migrations. The ledger refuses edits and deletes (tested).
- Added on the branch: indexes for `rate_requests(status, respond_by_at)`, `support_tickets(agency_id, created_at)` and `password_links(user_id)`. The migration is ready but **not applied to live**.
- Connections are reused per instance, now capped at 5, with timeouts, through Neon's pooler.
- `operationalIssues` still runs about 10 sequential queries; at 3 ms each and cached, this is acceptable for now.
- Backups: Neon's free plan keeps only a short restore window. A restore has **not** been tested.
- Volumes are tiny today, so index choices come from reading the code, not from production query statistics.

## I. Infrastructure recommendation

Keep it simple: one region, Singapore, for compute and database, with the CDN for static pages. No multi-region database is needed at this size. Do not move the database; Neon offered no Mumbai option in this setup.

Worth paying for when agents start booking:
- Vercel Pro: more frequent scheduled jobs. The cron is currently daily.
- A paid Neon plan: no idle sleep, longer restore window.
- Error tracking such as Sentry, and an uptime monitor pointed at `/api/health`.

Check current prices before buying.

## J. Needs your decision or access

1. **Default markups (most important).** `lib/services/settings.ts` sets 8% on best-rate quotes, 8% on group quotes and 20% on hotel extras, added before the agent sees the price; changeable in admin settings. Your hotel outreach says "no hidden markups", and the site says "direct". Decide: keep them and disclose them, set them to 0% and earn commission from hotels, or use another model.
2. **Approve going live:** merge `hardening-nov-2026`, apply the index migration, deploy.
3. **Real registration test** using `info+test@hotelbridge.co`.
4. **`ANTHROPIC_API_KEY`**, because the Diwali email promises AI features.
5. **Legal:** CA sign-off on GST and lawyer review of the hotel agreement, as listed in `docs/GO_LIVE.md`.
6. **Card or UPI payments** are not built. Bookings are paid by bank transfer recorded by finance.
